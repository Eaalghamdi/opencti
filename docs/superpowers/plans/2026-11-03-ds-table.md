# DataTable Restyle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Restyle OpenCTI's shared `DataTable` system — the hand-rolled, virtualized, GraphQL-paginated grid used across 87 files — onto the local `ds/` component library, in place, without changing its data/pagination/selection logic or its public `DataTableProps` API.

**Architecture:** `DataTable` is one shared component (`opencti-platform/opencti-front/src/components/dataGrid/`, 15 files, 4,267 lines) consumed by 87 call sites — restyling it once benefits all 87 automatically; this plan never touches a call site. New `ds/Checkbox`, `ds/Menu`, and `ds/Pagination` primitives (built the same way `ds/Combobox` wrapped Base UI's `Combobox`) replace the system's current mix of raw MUI and undeclared `@filigran/design-system`/bridge-component usage. Visual styling (`sx`/`styled()`/`theme.palette.*`) is replaced with `ds/tokens.css` variables and Tailwind utility classes; the virtualization math, GraphQL fragment pagination, column resize/reorder/visibility persistence, and selection logic are preserved exactly.

**Tech Stack:** `@base-ui-components/react@1.0.0-rc.0` `Menu` parts (confirmed installed at `node_modules/@base-ui-components/react/menu`, not yet used by this library), existing `ds/tokens.css` + `ds/lib/cn` + `ds/lib/useThemeMode`, Vitest + `@testing-library/react` + `@testing-library/user-event`.

**Spec:** `docs/superpowers/specs/2026-11-01-mui-to-local-ds-migration-design.md` (this is the other half of the spec's Phase 2 roadmap item — the Combobox half was completed in `docs/superpowers/plans/2026-11-02-ds-combobox.md`, whose Scope note explicitly deferred this work: *"the `DataTable` restyle (87 files, ~3,000 lines, GraphQL-pagination-coupled) is a separate, much larger, mostly-independent subsystem... it gets its own plan"*).

## Scope note (read before starting)

Recon (2026-11-03) corrected two things from the original estimate: the file count is 15 (not 9) and 4,267 lines (not ~2,983) — but the actual **styling surface is much smaller than that implies**: only 8 files use `sx=` (16 occurrences total), and only 1 file (`DataTableHeader.tsx`) uses `styled()` (3 components). Most of the line count is `dataTableUtils.tsx` (1,701 lines of cell renderers/formatters, almost none of it visual) and orchestration logic this plan does not touch.

A more significant finding: **this system already has partial, undeclared adoption of `@filigran/design-system` and bridge components** — `DataTableHeaders.tsx` and `DataTableLine.tsx` import FDS's `Checkbox` directly; `DataTableLine.tsx`, `DataTablePagination.tsx`, and `DataTableHeader.tsx` import `IconButton` from `src/components/common/button/IconButton.tsx` (a product-wide bridge that conditionally renders FDS's real `IconButton` or a MUI fallback); `dataTableUtils.tsx` imports FDS's `Chip` for one cell-value tag renderer. None of this is declared in `fds-migration/migration-state.json`'s `libComponentUsage` — it's invisible to `check-fds-conformity.mjs`, a pre-existing gap this plan did not create. This plan replaces all of it with `ds/` equivalents, continuing the project's standing decision (spec's "Decided" section, re-confirmed for the Combobox plan) to keep building the local library rather than route through the official FDS track — this is not a new fork in the road, just a larger application of the same already-made call.

**Real architectural risk, not a styling detail:** `DataTableBody.tsx`'s infinite-scroll is genuinely hand-rolled windowed virtualization (no third-party library) driven by a hardcoded `const ROW_HEIGHT = 49;` (line 164, documented as `theme.spacing(6)` (48px) + 1px border). Any task in this plan that changes row height, padding, or border width **must** update `ROW_HEIGHT` in the same commit, or the windowing math silently desyncs from actual rendered row height — rows will overlap or gap. This is called out per-task below where relevant, and is a standing constraint for every task that touches row layout.

`NestedMenuButton` (`src/components/nested_menu/NestedMenuButton.tsx`, 347 lines) is used by exactly one file in the whole app — `DataTablePagination.tsx`'s items-per-page submenu. It is not a shared product component despite its generic name; Task 8 replaces its role with the new `ds/Menu`'s submenu support. Deleting the now-unused file is in scope for that task if it ends up with zero remaining importers — confirm with a repo-wide grep before deleting, don't assume.

**Out of scope:** any of the 87 call sites' own prop usage (`DataTableProps`'s public shape does not change); `dataTableUtils.tsx`'s non-visual logic (cell value formatting, severity-string-to-color mapping logic itself — only the *token values* that logic resolves to are in scope, not the mapping logic); `useFilterEntityOptions`-style data-fetching hooks; the `react-draggable` column-resize mechanism itself (only its visual drag-indicator styling is in scope).

## Global Constraints

- **`ds/tokens.css`'s Tailwind utilities do not work outside `src/components/ds/`.** `ds/tokens.css:17-18` scopes Tailwind's content scanner to `@source "./"` (that directory only) — a class like `text-[var(--foreground)]` written in a `dataGrid/` file compiles to no CSS at all, silently. Found during Task 4; ruled on rather than left for each task to rediscover: in any file under `dataGrid/`, prefer rendering actual `ds/` **components** (`ds/Tooltip`, `ds/Checkbox`, `ds/Menu`, `ds/Pagination`, `ds/Button`) wherever a full swap applies — their own Tailwind classes work because the component files themselves live under `ds/`. For file-local layout/visual glue that isn't a full component swap (e.g. a header's own wrapper `<div>`), use `ds/tokens.css`'s CSS custom properties directly via inline `style` (`style={{ color: 'var(--foreground)' }}`) or `data-*`-attribute-driven React state for hover/drag/focus dynamics (Task 4's established pattern) — never a raw Tailwind utility class referencing a token. Do not widen `ds/tokens.css`'s `@source` scope to "fix" this; it exists to keep the `ds/` library's boundary clean.
- RTL-ready: logical CSS properties only, no hardcoded `left`/`right` (spec Goal 7) — this applies to inline `style` properties too (e.g. `paddingInlineStart`, not `paddingLeft`). Task 4's review caught exactly this in `DataTableHeader.tsx`'s new inline styles (physical `right`/`paddingLeft`/`paddingRight` copied forward unexamined from the old `styled()` CSS) — every task restyling onto inline `style` (the pattern the Tailwind-scoping constraint above now requires throughout `dataGrid/`) must check each property it writes against this rule, not just carry old physical values forward. `top`/`bottom` are block-axis, unaffected by RTL's inline-axis flip, and may stay physical. Task 4's review also flagged (out of scope for that task, not yet fixed) that `DataTableHeader.tsx`'s `IconButton` still has a pre-existing MUI `sx={{ marginRight: 1 }}` — whichever task next touches that `IconButton` usage should fix it in passing if convenient, though it is not that task's primary scope either.
- Reuse `ds/tokens.css` variables; never invent a new color/spacing/radius value.
- **Data/pagination/selection logic does not move.** GraphQL fragment pagination (`DataTable.tsx`), the hand-rolled virtualization in `DataTableBody.tsx`, column resize/reorder/visibility `localStorage` persistence, and `react-draggable` integration are restyled, never rewritten. A task that finds itself changing this logic has drifted out of scope — stop and report it as a concern rather than proceeding.
- **`ROW_HEIGHT` lockstep rule:** any change to row height, vertical padding, or border width in `DataTableLine.tsx` or `DataTableHeader.tsx` must update `const ROW_HEIGHT = 49` in `DataTableBody.tsx` to the new true value in the same commit, with a comment stating the new computation (mirroring the existing `theme.spacing(6) + 1px` comment). A task whose diff changes row dimensions without touching `ROW_HEIGHT` has a defect, full stop — the task's own reviewer must check this explicitly.
- `DataTableProps`'s public shape (`dataTableTypes.ts`) does not change — none of the 87 call sites may need a code change as a result of this plan.
- No direct HUMAIN DS visual reference exists for a data table (confirmed: not in the spec's reference inventory, Policy Guardrail never used one) — approximate using the already-established `ds/` visual language (`ds/Card`'s border/radius/shadow treatment, `ds/Select`'s and `ds/Combobox`'s popup/listbox styling for the new Menu) as the closest sibling primitives, not guessed independently.
- Base UI's `Menu` capability must be verified by reading the installed build at `node_modules/@base-ui-components/react/menu/*` before an approach is locked in — not assumed from memory of Base UI's docs.

## Review Focus

- A user scrolling an infinite-scroll table after any row-height-affecting style change must never see overlapping or gapped rows — the `ROW_HEIGHT` lockstep rule above is a Critical-severity finding if violated, not a style nit: Task 4 and Task 5 each add a test asserting `ROW_HEIGHT` matches the actual rendered row height.
- Column resize (drag) and column reorder (drag-and-drop) must keep working identically after `DataTableHeader.tsx`'s `styled()` components are replaced — the `react-draggable` integration itself is untouched, but its visual drag-indicator must still render and respond: Task 4 adds a test exercising the resize handle's visual state, not just that `react-draggable` is still wired up.
- Selected-row visual state must stay correct everywhere it's threaded — `DataTable.tsx`, `DataTableWithoutFragment.tsx`, `DataTableHeaders.tsx`'s select-all checkbox, and `DataTableLine.tsx`'s per-row checkbox all reference the same selected/active background token: Task 5 and Task 6 each add a test asserting the selected-state visual marker is present when a row/select-all is checked.
- The column-visibility menu must preserve exact toggle semantics (which columns are visible, persisted to `localStorage`) when its MUI `Menu`/`MenuItem` is replaced with the new `ds/Menu`: Task 6 adds a test toggling a column off and back on, asserting the `localStorage`-backed visibility state round-trips correctly.
- Keyboard accessibility of the new `ds/Checkbox` (row/select-all selection) and `ds/Menu` (column visibility) must not regress versus the current MUI/FDS behavior — Tab order, Space/Enter toggling, and screen-reader-visible state (`aria-checked`/`role="checkbox"` or `role="menuitemcheckbox"`): Task 1, Task 2, and Task 6 each add a keyboard-interaction test.
